# 仓库知识沉淀

## 概述

维护当前仓库内稳定、非显然、可复用且有证据的业务语义与实现约束。知识卡回答“以后需要记住什么”；包含固定执行方法的复杂知识应建议提炼为专项 Skill。

核心原则：先用当前代码和测试核实，再用最短形式记录；没有合格增量就不写文件。

## 每次触发时

### 任务开始前

1. 确定仓库根：Git 仓库使用目标文件所属的最近 Git root；非 Git 工作区使用当前项目根或用户明确指定的根。嵌套 Git root 属于另一仓库，不跨越边界读取知识。
2. 确定任务作用域：
   - 单项目仓库使用 `repo`。
   - monorepo 先以目标文件所属的最近项目/包清单确定项目；工作区清单和可核实的依赖或调用关系决定直接依赖。嵌套 `AGENTS.md` 约束其目录内的工作，但不单独证明项目边界；与清单冲突时核实实际构建和调用，不凭目录名猜测。
   - 无法可靠识别时退回 `repo`，不要猜测目录语义。
3. 如果 `<repo-root>/.agents/knowledge/INDEX.md` 存在，按顺序检索索引：目标路径/符号精确匹配，中英文业务术语及别名，目标项目作用域，已证实的直接依赖，最后是 `cross-project`。只读取命中卡片，不全量加载；索引不存在时正常继续，不创建空目录。
4. 核对命中卡片的状态、最后核验版本和证据，再用当前代码、测试、需求/业务确认及必要的运行证据验证。知识卡是线索，不是无需核对的最终事实。
5. monorepo 只加载目标项目、能由依赖或调用证据确认的直接共享组件，以及相关的 `cross-project` 知识。

### 任务结束前

按下表只执行一种最小动作：

| 情况 | 动作 |
| --- | --- |
| 没有合格增量 | 不创建或修改知识文件，也不输出知识报告 |
| 有稳定新结论 | 新建或合并短知识卡并更新索引 |
| 既有结论变化 | 修订原卡和索引，并核对同主题旧结论 |
| 既有结论失效 | 有替代路径时标记 `deprecated` 并指向替代卡；无保留价值时删除卡片和索引项 |
| 业务含义待确认或证据冲突 | 标记 `needs-review` 或 `conflicted`，记录待确认事项；不把任一说法当作当前事实 |
| 首次出现高成本故障 | 符合条件时只记入待观察问题，不创建完整问题卡 |
| 已成为复杂执行方法 | 建议用户考虑提炼专项 Skill，不自动创建 |

如果用户要求只分析、不修改文件或限制写入范围，不更新知识文件；可以简短报告已经有证据的候选知识，但不能声称已经沉淀。

### 最终回复保持安静

- 只有实际新增、修订或删除了知识文件时，才在最终回复中用一句话说明变更的知识条目。
- 没有修改知识文件时，不要提“无知识增量”“未创建知识库”“本次不沉淀”或内部判断过程；直接交付用户任务本身。
- 只分析任务中发现候选知识时，仅当它会帮助用户后续决策才简短提示，并明确“候选、尚未写入”。
- 用户明确询问知识库状态、Skill 行为或评测结果时，可以如实说明知识处理情况。

## 知识准入

普通知识必须同时满足：

1. 不容易从单个函数、类型、文件名或局部代码直接看出；
2. 未来类似任务仍会复用；
3. 会影响未来的实现、分析、调试或审查决策；
4. 有可追溯的业务确认、代码、测试或运行证据；只有推断时不能形成当前结论。

知识类型可为业务规则、术语、状态流、跨文件联动、故障处理或架构约束。适合记录跨文件业务流程、隐含修改联动、项目特有验证方法，以及权限、事务、并发、缓存、审计或同步机制的组合约束。类型用于检索，不是要求为每种类型创建卡片。

不要记录修改文件清单、临时日志、普通拼写错误、一次性过程、公共技术文档已经充分说明的用法，或能从局部代码直接读出的事实。

## 仓库与作用域边界

- 所有路径都以当前 `<repo-root>` 为基准。不要读取父目录、相邻仓库或用户级知识目录。
- 这个 Skill 只按仓库级方式工作，不创建或依赖用户级知识库。
- 复制到其他仓库时只复制 Skill 本体，并把触发规则合并到目标仓库的根 `AGENTS.md`；不要复制来源仓库的 `.agents/knowledge/`。
- 单项目知识使用 `repo` 作用域；项目知识使用稳定项目名或包名；跨多个项目成立的知识使用 `cross-project`。
- 跨项目知识只保留一份。知识文件名使用作用域前缀，例如 `billing-refund-audit.md` 或 `cross-project-auth-boundary.md`。
- 只有在索引继续增长且检索明显变慢时，才按作用域增加子索引，不按卡片数量机械拆分。

## 事实、证据与状态

- 分开写业务事实（需求或业务方确认的规则）、实现事实（当前代码行为）、测试事实（测试覆盖的情形）、运行事实（指定环境与时间的观测）和推断。实现事实不能单独证明业务本意；测试通过也不能证明未覆盖的业务规则；运行观测不能脱离环境成为通用规则。
- 证据注明类别、来源和可定位标识。优先记录稳定的仓库相对路径、符号、测试名、需求编号或可追溯的确认记录；行号只能作辅助。记录最后核验的提交或版本；若工作树未提交，注明核验基准及未提交状态，不能把基准提交说成已包含变更。
- `current`：结论与已核实证据一致；`needs-review`：版本变化、证据不足或业务含义待确认；`conflicted`：权威需求与实现，或不同有效证据之间有未解决冲突；`deprecated`：规则不再适用，但需要保留迁移指向。旧卡缺少状态时先当线索核实，不默认 `current`。
- 命中 `needs-review`、`conflicted` 或 `deprecated` 时，不直接引用为当前事实。先核验；能解决则更新状态、结论和证据，不能解决则在答复中说明未知或冲突。`deprecated` 只提供历史与替代路径。
- 业务确认/需求与代码不一致时，保留双方的原话、范围及差异，标记 `conflicted`；不得把实现倒推成业务结论，也不得仅凭需求描述断言当前运行行为。推断可写在待确认事项中，并标明验证办法，不能写进当前结论。

## 最小存储格式

首次产生合格知识或合格待观察问题时才创建 `.agents/knowledge/INDEX.md`。

```markdown
# 仓库知识索引

| 作用域 | 路径/符号 | 业务词/别名 | 状态 | 知识 |
| --- | --- | --- | --- | --- |
| `billing` | `services/billing/refund.ts`、`refundOrder` | 退款、refund | `conflicted` | [退款联动](billing-refund.md) |

## 待确认事项与冲突

| 主题 | 作用域 | 待确认内容与证据 | 对应卡片 |
| --- | --- | --- | --- |
| 退款完成时点 | `billing` | 需求 R-12 与 `refundOrder` 的时点不同；待业务确认 | [退款联动](billing-refund.md) |

## 待观察问题

| 问题特征 | 作用域 | 出现次数 | 当前结论 |
| --- | --- | ---: | --- |
| CI 上传偶发超时 | `repo` | 1 | 根因待确认 |
```

索引只保留有内容的小节；上例的冲突表与待观察表展示两种不同用途，不要求同时创建。

普通知识卡保持简短，字段只填写能帮助未来判断的内容：

```markdown
# 标题

作用域：
- `repo`、项目名或 `cross-project`

类型与状态：
- 业务规则 / 术语 / 状态流 / 跨文件联动 / 故障处理 / 架构约束；`current` / `needs-review` / `conflicted` / `deprecated`

适用：
- 相关路径、符号或任务条件

业务语义（业务卡按需填写）：
- 对象/角色、触发条件、状态或生命周期、不变量、例外、权威来源

已确认结论与实现边界：
- 分别说明业务规则与当前代码行为；不能证明的一方不补写

联动：
- 修改某处时必须同步检查的内容

证据与最后核验：
- 证据类别、需求编号或仓库相对路径及符号/测试名；提交或版本

待确认事项/冲突（仅在需要时）：
- 双方说法、各自证据、缺口和确认方式；推断明确标注
```

不复制大段源码，不补写长篇背景。Git 保存历史，卡片本身不维护版本章节。`needs-review` 或 `conflicted` 卡片可以保留已证实的局部事实，但不得给出未确认的统一结论。

## 索引与卡片的维护

- 新建、修订、迁移或删除卡片时，同次更新索引中的作用域、路径/符号、业务别名、状态和链接；修改后检查链接目标存在、卡片有索引入口，同主题没有两张 `current` 卡且旧结论未残留。只修改用户授权范围内的文件；受限时报告无法同步的部分，不留下假装完整的更新。
- 代码或需求变更触及卡片证据时，重新核验相应结论。暂时无法核验就标记 `needs-review`；证据相抵触且无法解决就标记 `conflicted` 并登记“待确认事项与冲突”。这个表记录业务未知或证据分歧，不计入故障的“待观察问题”次数。
- 发现断链、重复卡或孤立卡时先确认实际来源和作用域，再修复索引或合并卡片；不要靠删除未经核实的知识消除告警。

## 重复错误和问题

第一次出现的问题只有同时满足“原因不明显、排查成本较高、可能再次发生、有具体证据”时，才进入 `INDEX.md` 的“待观察问题”。不要在第一次出现时创建完整问题卡。

第二次出现相同或相似现象时，先比较当前证据和根因：

- 确认同根因且已有复用结论：更新次数，创建问题卡，并从待观察表移除。
- 错误文本相同但根因不同：分开记录。
- 现象重复但根因仍未知：只记录已证实现象、安全排查边界和未知项，不把推测写成事实。

问题卡使用：

```markdown
# 问题标题

作用域：
- `repo`、项目名或 `cross-project`

类型与状态：
- 故障处理；`current` 或 `needs-review`

现象：
- 可识别的问题特征

已确认：
- 已有证据支持的根因或边界

处理：
- 安全且可复用的处理方式

避免误判：
- 容易混淆但根因不同的情况

证据：
- 脱敏的日志特征、代码路径与符号、测试名或验证记录；最后核验提交或版本
```

## 何时建议专项 Skill

以下信号满足两项以上时，建议用户考虑提炼独立 Skill：

- 有固定顺序的工作流；
- 漏步骤会造成数据、权限、兼容性或部署风险；
- 有多条件分支和冲突处理；
- 每次都要使用固定检查清单；
- 需要专用脚本、模板、测试或验证命令；
- 已在多次任务中反复使用；
- 知识卡超过约 80 行，继续压缩会丢失关键规则。

建议时给出名称、触发条件和晋升原因。是否创建由用户决定，本 Skill 不自动创建。专项 Skill 创建并验证后，在原卡只保留触发说明、Skill 名称及必要的事实来源，删除重复执行正文；同步更新索引并检查全文，确保执行规则只有一处权威来源。

## 冲突和安全

- 卡片与当前代码或测试冲突时先核实。新语义证据明确则同任务修订或删除；仍有业务歧义则标记 `conflicted` 并报告待确认点。
- 不保存令牌、密码、Cookie、签名 URL、真实凭据、敏感配置值或不应进入版本控制的内部信息。
- 当前工作树有无关改动时，只修改知识相关文件，不整理、覆盖、暂存或提交其他改动。
- 不因为时间紧、已有旧结论或错误文本相同而降低证据要求。

## 常见错误

| 错误 | 正确处理 |
| --- | --- |
| 每次任务都创建卡片 | 四项准入条件必须同时满足 |
| 开始任务就创建空索引 | 首次有合格内容时再初始化 |
| 一次错误直接写完整问题卡 | 先进入待观察问题，复发且同根因后晋升 |
| 扫描并加载全部知识 | 先查索引，只加载匹配作用域和关键词的卡片 |
| 旧卡覆盖当前代码事实 | 重新核实并修订、删除或报告歧义 |
| 复制 Skill 时复制知识 | 每个仓库独立积累知识 |
| 把复杂流程继续塞进长卡 | 满足两项信号后建议专项 Skill |
| 把“未沉淀”写进每次交付 | 没有知识文件变更时完全静默 |

## 示例

修改退款服务时，索引命中目标项目的“退款联动”和 `cross-project` 的“审计边界”。先用当前服务、测试和调用关系验证两张卡，再完成修改。若只发现本次新增的局部条件分支，不沉淀；若确认“所有退款成功路径都必须在事务提交后写入统一审计事件”是跨文件、稳定且有测试证据的联动，则更新目标项目知识卡。若这项规则进一步发展为多分支、固定步骤和专用测试清单，则只建议提炼退款审计 Skill。
